# 目标、输入和实际完成范围

## 输入条件

- 已能在 iOS 运行的 Unity 原生包：`SilksongNative-0.8.2`。
- 独立资源包：`SilksongResources-v1-fixed.zip`；原资源由应用在自己的 Documents 中加载。
- 用户没有可重建的 Unity 主工程。
- 开发环境：用户 Mac、Xcode、本地 `iPhoneOS27.2.sdk`、Python 3。
- 设备信息主要来自用户的尺寸图、诊断 JSON、截图和手动反馈。没有在此仓库中保存设备标识或完整聊天。

## “原生”在这里分三层

| 层 | 本案例状态 |
| --- | --- |
| 程序在 iOS 上原生执行 | 输入 IPA 已经具备；不是此轮从零生成 |
| 窗口能使用折叠设备的实际区域 | 本轮通过 scene 生命周期和兼容补丁逐步补齐 |
| 游戏画面、相机、输入和 UI 跟随新区域 | 本轮主要工程工作：分区、比例、HUD、键位、编辑器与反馈 |

不能从“窗口铺满”推导出“游戏已完整适配”，也不能从“ARM64”推导出“另一平台二进制能直接在 iOS 跑”。

## 最初症状

删除全屏限制后，0.2.3 诊断仍是 `375×667 pt`／`667×375 pt`，用户标记内外屏和半折叠后尺寸没变。Unity 主程序报告旧 SDK 标记，触控组件的较新 SDK 不会自动替换主程序的窗口行为。

本案例先比较配置变更，再实验 launcher/scene 桥接，最后处理游戏实际渲染和输入。它不是 Apple 对任意旧应用的通用兼容承诺。

## 最终资产分工

- `src/`：自编 Objective-C/C 桥接实现，含该游戏专用 ABI 绑定。
- `manifests/`：已审核引擎补丁范围、默认布局。
- `tests/`：布局、策略、ARM64 分支和本机进程采样检查。
- `tools/`：可在新目录使用的构建、测试、身份校验和打包工具。
- `evidence/`：保留原报告；收尾截图另记新增证据，避免改写历史。
- `assets/`：用户提供的皮肤图和收尾截图；游戏本体与资源包不随仓库分发。

## 整理时做的取舍

旧目录里的历史 `package.py` 依赖绝对路径及前一个版本，不适合作为下次 AI 的唯一入口。因此这里保留历史报告和补丁清单，另提供参数化工具；最新桥接源码保持原样。重打包基线默认限定为已识别的 0.2.18/0.2.19，不能把它直接注入陌生 IPA。
