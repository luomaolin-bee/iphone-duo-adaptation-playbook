# 把方法用到另一款游戏

## 先判断输入

| 输入 | 合理路线 | 本仓库能提供什么 |
| --- | --- | --- |
| 完整Unity/其他引擎工程 | 用目标iOS SDK重建，正式接入窗口、分区、相机、HUD与触摸 | 几何思路、布局编辑模型、视觉/诊断设计 |
| 已能跑的iOS IPA，无工程 | 先检查结构、版本、生命周期、输入与渲染，做有限兼容实验 | 复盘方法、身份验证、测试与可回退流程；绑定需重新实现 |
| PC/Switch等其他平台二进制/资源 | 先解决引擎源码/平台API、图形/输入/文件系统与资源兼容、iOS构建链 | 只能在已有iOS运行基底之后接入设备适配；不是自动翻译器 |
| 只有游戏画面/视频 | 只能做交互原型或视觉演示 | 不能据此生成真实游戏实现 |

## 有工程时的优先设计

1. 使用scene/window的实际区域，监听尺寸与姿态变化。
2. 明确横向overlay和竖向/半折叠deck布局，不依赖设备型号写死坐标。
3. 游戏view与render target保持同一目标比例；相机矩形、Canvas/HUD重新布局。
4. 为菜单、战斗、地图等定义清晰输入状态，直接复用游戏动作系统。
5. 原生触摸的选择/确认按真实UI事件实现；测试长按、多点、拖动、返回，不拿坐标猜命令。
6. 把视觉效果做成可降级组件，分离于命中和游戏逻辑。
7. 用诊断与真机矩阵验证。

有源码时不应优先复制本案例的固定字节补丁。

## 只有IPA时的调查表

- 是哪种CPU/引擎/版本？是否已经是可运行的iOS构建？
- launcher、引擎framework、资源、补丁库、Info.plist分别是谁负责？
- 使用哪个窗口/scene生命周期？实际bounds是否已变化？
- 游戏渲染层是Metal还是其他后端？实际drawable多少像素？
- 相机是否有固定纵横比或方向排序？HUD是否另有相机/Canvas？
- 原输入动作和确认/返回策略是什么？是否已有自定义触控组件？
- 符号/元数据是否可读？原生ABI与托管对象生命周期能否核实？
- 当前证据能否明确定位问题？有没有已知可回退包？

若无法核实某个地址或字段，不应靠关闭断言让固定地址代码继续运行。可以先只交付布局/视觉演示，明确它尚未接入实际游戏。

## 可以抽象的模块

五形态布局的状态机、归一化控制点、浮动编辑器、可访问性降级、GPU小图倒影思路、元数据缓存、限频/单帧在途、监测口径和证据登记。

必须重新绑定的模块：TPPad接口、HID动作表、菜单映射、场景/生命字段、HUD节点名、纹理获取方式、引擎函数与Mach-O补丁地址。保留接口，替换游戏适配器，而不是复制整个0.2.19并改一个标题。
